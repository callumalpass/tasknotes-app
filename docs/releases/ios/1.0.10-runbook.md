## Platform checks and limits

- Android already uses `@capacitor/push-notifications` for FCM tokens,
  foreground signals, notification taps and token rotation. `MainActivity`
  inherits Capacitor's intent dispatch and uses `singleTask`.
- iOS already forwards APNs registration to `@capacitor-firebase/messaging`,
  which returns FCM tokens and routes foreground/tap/rotation events. Its
  `createChannel` is unsupported on iOS; the shared adapter must tolerate that
  rather than require an Android channel. No additional native adapter is needed.
- Both ordinary CI jobs deliberately omit Firebase configuration and push
  plugins. They build, install, launch and restart the bundled shell only.
  iOS disables signing; Android uses its disposable debug signature, not a
  release key. The Node regression check protects this credential isolation;
  existing manager/adapter unit tests cover the JS event contract independently.

Configured-plugin compilation and live FCM/APNs delivery remain unverified: no existing credential-free Firebase fixture route was found and no iOS device is available; neither is a source-completion gate, and no simulator/emulator run is claimed locally.

FCM rotation refreshes the selected collection; other opted-in collections refresh when reopened.

Rare transport/OS delivery outcomes remain at-least-once, not exactly-once display.

## Owner-only release sequence (do not execute during implementation)

1. Finish SDK intake and reminder acceptance above. Resolve the already-submitted
   1.0.10 with the release owner before choosing a version. No duplicate bump is
   needed: #315 already aligned package/Xcode versions and added release metadata.
   If Apple no longer permits replacing that version, prepare a separate later
   version in a PR. Update the chosen version's review notes and What's New for
   all existing store locales only after reminder qualification; do not claim
   reminders in the already-uploaded binary. Verify the chosen release policy
   (MANUAL versus automatic) explicitly; do not assume MANUAL from this runbook.
   Never copy private review credentials into Git.
2. Qualify the final source head once through the owner's agreed CI round;
   record its SHA and results. No release tag or workflow dispatch is part of
   that qualification. Release only the subsequently approved source on `main`.
3. After separate signing approval, use **iOS release** (`ios-release.yml`) on
   that approved `main`, inputs `version=1.0.10`, `upload=false`,
   `submit_public=false`. This produces a signed IPA artifact, not an upload.
   The workflow requires iOS SDK 26+, existing signing/Firebase configuration,
   and uses `GITHUB_RUN_NUMBER` as the build number. Its `>25` guard is not a
   freshness check: confirm the build exceeds the latest uploaded build before
   authorizing it. No live store/build state was queried here.
4. After separate signing **and** TestFlight approval, run the same workflow
   with `version=1.0.10`, `upload=true`, `submit_public=false`. It rebuilds and
   signs a **new** build; it does not upload the previous IPA. Alternatively,
   authorize signing+upload together and do only this run instead of step 3.
   Record the successful uploaded workflow run ID, SHA, version and build.
5. Only after separate store approval, use **App Store submission**
   (`app-store-submit.yml`) on approved `main`,
   `source_run_id=<successful uploaded workflow run ID>`, `submit=true`,
   `release=false`; approve the `app-store-production` gate. This promotes that
   exact upload without rebuilding. Verify the actual metadata release policy:
   automatic release can make the app public after approval. For MANUAL policy,
   a separate owner-approved `release=true` run is required after Apple approval.

For the owner only, after resolving version availability, replace `VERSION`
with the approved marketing version and `RUN_ID` with the new successful upload
run (never the pre-reminders run above):

```sh
# Optional signing-only qualification; this does not upload.
gh workflow run ios-release.yml -R callumalpass/tasknotes-app --ref main \
  -f version=VERSION -f upload=false -f submit_public=false
# Separate authorized signing + TestFlight upload; creates a new build.
gh workflow run ios-release.yml -R callumalpass/tasknotes-app --ref main \
  -f version=VERSION -f upload=true -f submit_public=false
# Separate authorized review submission of that exact upload.
gh workflow run app-store-submit.yml -R callumalpass/tasknotes-app --ref main \
  -f source_run_id=RUN_ID -f submit=true -f release=false
```

Steps 3–4 use `1.0.10` only if the owner confirms it is still eligible; otherwise
use the newly reviewed version consistently. None of these commands was run by
this handoff.
